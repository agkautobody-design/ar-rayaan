# Hadi: answering on its own, and the hosted-AI tier

Status: built, switched off. No billing, no prices, no real AI endpoint, and
(owner decision, Oct 2026) NO usage caps yet.

## Goal

Hadi should answer from the app's own verified content so that a hosted AI
call is rare. Every call avoided is cost avoided.

## How a question is answered (in order)

1. Safety first: crisis, child-safety, grief, personal rulings. Always local.
   Never sent anywhere, never counted as hosted.
2. The built-in checked shelf (`OfflineHadiProvider`, hand-written, cited).
3. Local knowledge (`lib/features/hadi/data/local_knowledge.dart`): a
   tokenised, spelling-normalised, alias-aware, one-typo-fuzzy index over the
   Huda guides (51), the Q&A bank (12) and the story packs (prophets,
   companions, women, seerah, the unseen, signs, tales, daily duas, new
   Muslim, modern hadith). It scores every entry and gives a confidence.
   - At or above 0.72, with a clear margin over the runner-up and most of the
     question covered by the entry's title words: Hadi answers alone, by
     QUOTING the entry (its own title, steps and source line, an unverified
     story is labelled as such first). Zero API calls.
   - Between 0.5 and 0.72: the closest entry is offered as a button
     ("Closest in my library") and only then may hosted AI be considered.
   - It never runs for a question about where something is in the app, a
     time or a nearby place (those go to the screen), nor for "what does X
     mean" against a story.
4. Hosted AI, only if all hold: no own API key, a backend exists, the
   question is Islam-related, not ruling-shaped (halal, haram, can I, should
   I), not medical, and not a safety case.

Own-key users keep their existing path.

## API-cost reducers on the hosted path

| Reducer | Where |
| --- | --- |
| Normalised-question answer cache, persisted, 30-day TTL, 100 entries, keyed by school of law too | `hosted_cache.dart` |
| Repeats cost nothing (same question, any case or punctuation) | cache hit, counted as `cache` |
| Short prompt: top 2 passages only, last 4 messages, question cut to 500 chars, no app table of contents | `hadi_controller.dart` |
| Hard output cap sent to the server (350 tokens) and replies shortened to the package's max length | `hosted_ai.dart` |
| Small-model-first flag (`preferSmallModel`) sent as a hint | `hosted_ai.dart` |
| No hosted call for greetings, app help, crisis, safety, out-of-scope | gates above |
| Failed call: nothing counted, nothing cached | `HostedHadiProvider` |

Not built: a SHIPPED seed cache. A seed would be pre-written AI answers to
common questions; those would be new religious content and need scholar
approval (see `docs/content_needed/hadi_gaps.md`). The mechanism is ready.

## Every hosted reply

Passes the same reference verifier and ruling filter as any live reply, and
ends with: "AI-generated, may be wrong. Check with a scholar."

## Packages (dormant)

`lib/app/core/packages/hadi_package.dart`: `free`, `plus`, `family` (names are
placeholders, TODO-OWNER) with ONE table of limits. Every limit is null
(unlimited) and nothing is shown to the person. To switch caps on later,
set numbers in that table and enforce them on the server. `UsageMeter` is
already wired and only counts while limits are null.

The older managed-key quota (`SubscriptionService.consumeQuestion`, Hadi and
Wasia) is untouched. It should be retired when the proxy exists.

## Local counters (no telemetry)

`hadi_stats.dart` counts, on the device only: `local`, `miss`, `hosted`,
`cache`, `failed`, `safety`. Founder Console shows "answered N% without a
hosted call". No question text is stored. Cache hits count as local.

The 85% target for verified-source answers is NOT reached. The remaining

`docs/content_needed/hadi_gaps.md`. Closing them needs owner/scholar
approved content, not code. Many "pointed" questions are correct app-help
answers (find a masjid, change language), which is the right local answer.

## Security: the real cap lives on a server

A cap kept on the phone can be reset. If caps are ever switched on, the
backend must be a server proxy that holds the provider key (the app ships no
secret), authenticates the user, checks entitlement itself, enforces the cap
per user, applies the guardrail prompt on its side, and logs counts not
conversation text. The app maps a server cap response to `HostedAiCapReached`
and falls back to the library.
